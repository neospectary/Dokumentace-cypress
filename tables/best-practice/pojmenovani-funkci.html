Popisné pojmenování funkcí, helperů a custom commandů

Dobrý název funkce nebo příkazu nahradí komentář. Čtenář by měl z názvu okamžitě pochopit, co funkce dělá — bez toho, aby musel číst její tělo. Platí to dvojnásob v Cypressu, kde testy čte celý tým včetně QA, vývojářů i product ownerů.

Proč na názvu záleží

Špatně pojmenovaná funkce zvyšuje kognitivní zátěž — každý, kdo test čte, musí dohledávat, co funkce vlastně dělá. Dobře pojmenovaná funkce se stává živou dokumentací a usnadňuje údržbu i onboarding nových členů týmu.

❌ Anti-pattern — název nic neříká

// Co tohle dělá? Musím číst implementaci.
cy.doStuff()
cy.handleUser()
cy.process()
cy.action('submit')

✅ Správně — název je samopopisný

// Jasné na první pohled.
cy.loginAsAdmin()
cy.fillRegistrationForm({ name: 'Jan', email: 'jan@test.cz' })
cy.submitOrderForm()
cy.verifySuccessToast('Uloženo')

Pravidla pro pojmenování custom commandů

Custom commandy jsou veřejné API tvého test-suite. Název musí být camelCase, začínat slovesem a vystihovat akci — ne implementaci.

Vzor: sloveso + objekt (+ kontext)

// Sloveso + objekt
cy.login()
cy.logout()
cy.fillForm()
cy.submitForm()
cy.openMenu()
cy.closeModal()

// Sloveso + objekt + kontext (kdy existuje více variant)
cy.loginAsAdmin()
cy.loginAsGuest()
cy.fillShippingForm()
cy.fillBillingForm()

// get + selector type — pro helper selektory
cy.getBySel('submit-button')        // hledá [data-cy="submit-button"]
cy.getBySelLike('user-row')         // hledá [data-cy*="user-row"]

Délka názvu — kdy přidat detail

// Příliš obecné — co přesně otevírá?
cy.open()

// Příliš dlouhé — zbytečné slovo "the"
cy.openTheUserProfileSettingsPage()

// Správná míra — jasné, úsporné
cy.openUserProfile()
cy.navigateToSettings()
Špatný název Dobrý název Proč?
cy.auth()cy.login()Sloveso jasně říká akci
cy.doSearch()cy.searchFor(query)Parametr je součástí názvu
cy.populateData()cy.fillContactForm(data)Specifikuje, který formulář
cy.proceed()cy.confirmDeleteDialog()Říká, co se potvrzuje
cy.check()cy.verifyUserIsLoggedIn()Popisuje konkrétní aserce

Pravidla pro helper funkce

Helper funkce jsou zpravidla čisté JS/TS funkce (nikoli Cypress příkazy). Stejné pravidlo: sloveso + objekt, camelCase, žádné zkratky.

✅ Dobře pojmenované helpery

// Gettery — vrací hodnotu
function getUserFullName(user) { ... }
function getFormattedDate(date) { ... }
function getActiveFiltersCount(filters) { ... }

// Akce — provádějí operaci
function generateRandomEmail() { ... }
function buildApiUrl(endpoint, params) { ... }
function parseErrorMessage(response) { ... }

// Predikáty — vrací boolean, název začíná is/has/can
function isValidEmail(email) { ... }
function hasAdminRole(user) { ... }
function canUserEditRecord(user, record) { ... }

❌ Špatně pojmenované helpery

function data() { ... }          // Co za data?
function process(x) { ... }      // Co zpracovává?
function util(type, val) { ... } // Universální název = žádný název
function fn() { ... }            // Absolutně nic neříká

Vzor pro helpery v beforeEach

// helpers/user.ts
export function createTestUser(overrides = {}) {
  return {
    name: 'Test User',
    email: 'test@example.com',
    role: 'viewer',
    ...overrides,
  }
}

// Ve spec souboru
beforeEach(() => {
  const user = createTestUser({ role: 'admin' })
  cy.setupUser(user)
})

Pojmenování describe() a it() bloků

Test runner zobrazuje názvy bloků jako věty. Kombinace describe + it by měla dávat smysl přečtená za sebou.

✅ Správně — čte se jako věta

describe('Přihlašovací formulář', () => {
  context('když uživatel zadá neplatné heslo', () => {
    it('zobrazí chybovou hlášku', () => { ... })
    it('neodešle formulář', () => { ... })
  })

  context('když uživatel zadá správné údaje', () => {
    it('přesměruje na dashboard', () => { ... })
    it('uloží session token', () => { ... })
  })
})

❌ Špatně — technický popis bez kontextu

describe('test login', () => {
  it('should should work', () => { ... })       // duplicitní "should"
  it('test1', () => { ... })                    // čísla nic neříkají
  it('checks the thing', () => { ... })         // co je "the thing"?
  it('should redirect to the landing page', () => { ... })  // "should" je zbytečné
})
BlokDoporučeníPříklad
describe()Název stránky nebo komponenty'Stránka uživatelů'
context()Začínej "když" nebo "pokud"'když uživatel není přihlášen'
it()Imperativ bez "should"'zobrazí přihlašovací formulář'

Pojmenování Page Object metod

Page Object třídy seskupují selektory a akce jedné stránky. Metody by měly být pojmenovány stejně jako custom commandy — sloveso + objekt.

✅ Správný Page Object

// pages/LoginPage.ts
export class LoginPage {
  // Gettery — vracejí element (getter pattern)
  getEmailInput()    { return cy.get('[data-cy="email-input"]') }
  getPasswordInput() { return cy.get('[data-cy="password-input"]') }
  getSubmitButton()  { return cy.get('[data-cy="submit-button"]') }
  getErrorMessage()  { return cy.get('[data-cy="error-message"]') }

  // Akce — provádějí sekvenci kroků
  fillEmail(email: string)       { this.getEmailInput().type(email) }
  fillPassword(password: string) { this.getPasswordInput().type(password) }
  submit()                       { this.getSubmitButton().click() }

  // Kompozitní akce — kombinují více kroků
  loginWith(email: string, password: string) {
    this.fillEmail(email)
    this.fillPassword(password)
    this.submit()
  }
}

Pojmenování souborů Page Object

// ✅ kebab-case pro soubory, PascalCase pro třídy
pages/login-page.ts        → class LoginPage
pages/user-list-page.ts    → class UserListPage
pages/checkout-page.ts     → class CheckoutPage

// ❌ nekonzistentní
pages/LoginPage.ts
